# MinIO 附件备份与一致性

ERP 的 `sys_attachments` 保存业务关联、对象键、大小、SHA-256 和状态；私有 MinIO bucket 保存文件正文。两份数据必须按相近时间点备份与恢复。当前开发配置指向现有 MinIO 服务的 ERP 专属 bucket；其他项目即使共用服务，也不能备份、删除、公开或覆盖其 bucket。JAR 只持有外部 endpoint 和最小权限凭据，不包含对象。未经管理员确认，不能推断 MinIO 宿主目录、持久化卷或快照位置。

由 MinIO 管理员确认服务部署方式、持久化介质、ERP bucket 所有权、私有策略、对象版本与加密策略。推荐使用现有存储平台的快照或受限凭据将 ERP bucket 镜像到受保护的离机目标，记录时间点、对象数、容量、校验摘要和失败项；本机未发现 `mc` 客户端，也没有获准的备份目标，因此本阶段不声称对象备份成功。若管理员已通过安全机制配置好 `mc` alias，可先用只读 `mc ls <erp-alias>/<erp-bucket>` 和 `mc stat <erp-alias>/<erp-bucket>/<known-object-key>` 检查，再在获准的备份目标执行镜像；不要把 Access/Secret 写在命令参数、脚本、日志或 Git 中。备份目标应限制访问并防止跨项目覆盖。

恢复顺序：确认数据库备份与对象快照时间点 → 在隔离 MinIO/bucket 先恢复对象 → 将配套 MySQL dump 恢复到隔离 MySQL → 以隔离环境运行应用和权限检查 → 抽样下载并比对元数据的大小/SHA-256 → 再计划正式恢复。正式环境 bucket 覆盖或对象删除必须获得管理员审批，不在当前开发 bucket 演练。

只读一致性核查应分三组：`READY` 元数据对应的对象是否存在且大小/摘要一致；ERP bucket 对象是否有对应元数据（包括 `DELETE_PENDING` 和 `DELETED` 状态）；元数据的业务类型/ID 是否仍存在且当前用户有权访问。对象存在不等于所有用户可下载，后端每次仍按原业务权限和 ALL/DEPARTMENT/SELF 范围校验。数据库与对象备份时间不同可能出现两侧不一致，必须逐项记录并人工判断，不能自动批量删除“孤儿”文件。当前没有后台对象一致性修复服务、病毒扫描或已验证的对象恢复演练。
