# 站内通知

Phase 10C 使用 `sys_notifications` 持久化当前用户收件箱。通知只有简短标题、摘要和关联业务类型/ID，不复制设备档案或长文本。标题和摘要由服务端固定文案及业务编号组成；Vue 模板按普通文本渲染，不执行 HTML。

## API 与权限

`GET /api/notifications?page=1&size=20` 返回 `PageResult`，`GET /api/notifications/unread-count` 返回未读数，`GET /api/notifications/{id}` 仅返回本人通知，`PATCH /api/notifications/{id}/read` 单条已读，`POST /api/notifications/read-all` 标记本人全部未读。全部接口必须登录并拥有 `notification.view`；SQL 始终按 `recipient_user_id` 限制。系统管理员、仓库管理员、部门负责人、管理层、员工角色均有该权限，但不能越权读其他人的通知。前端顶栏显示未读数，通知页支持分页、单条或批量已读；进入关联业务前再向原详情接口验证权限与存在性，不把通知本身当作授权。页面切换与已读操作后刷新未读数，无轮询、WebSocket 或外部推送。

## 触发与防重

入库/出库正式执行完成向创建人通知；领用正式发放向申请人通知；维修完成或无法修复、保修拒绝或完成、换货执行完成向申请人通知。接收人来自真实单据字段；接收用户不存在或停用时 `INSERT ... SELECT` 不产生记录。普通查询、审批中间态与重复重试不生成通知。`(event_key, recipient_user_id)` 唯一键按业务类型和单据 ID 防重，重复动作会被原状态/version/请求幂等逻辑拦截。通知和业务写入在同一个数据库事务，业务回滚时通知一起回滚；通知数据库写入失败会回滚本次核心业务，避免出现业务成功而通知状态不明的半提交。通知内容仅给接收人可见，关联业务始终重新校验原业务权限与 `ALL/DEPARTMENT/SELF` 范围。

V18 新增真实用户外键、事件唯一键与收件箱索引。通知属于站内记录，没有邮件、短信、浏览器推送或后台定时扫描。业务对象日后删除或用户权限变化时，通知历史仍在，但前端会显示目标不可访问的提示。
